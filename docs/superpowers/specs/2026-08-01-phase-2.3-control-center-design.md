# Picotoo Pet V2.3 Windows Control Center 设计规格

- 文档状态：Draft → Review
- 设计日期：2026-08-01
- 基线分支：`main`
- 基线提交：`4ef2634ec24666d8995874d44bbf5b0e238d450a`
- 目标版本：`2.3.0`
- 适用范围：Phase 2.3 Windows Control Center 可用性重构
- 不适用范围：Phase 3 Generic Connector 的完整实现、Phase 6 Windows Media Worker、视频生产闭环及后续阶段

## 1. 目的

本规格将现有 Windows Desktop 从“连接与任务链路工程切片”重构为 Picotoo Pet 双机平台的日常 Control Plane UI。它负责聚合项目、任务、结果、审批、健康、自动化状态和诊断入口，但不成为任务事实源，也不直接执行 ComfyUI 或其他 GPU 工作流。

本规格只设计 Phase 2.3，不重新讨论已经冻结的总体技术栈，不扩展 V1，不要求用户在 Windows 电脑上编译、安装 SDK 或运行反复修补脚本。

## 2. 冻结约束

以下内容作为已批准决定直接执行：

1. Windows Desktop 继续采用 WPF、MVVM 和原生 Windows CI。
2. Mac Core、SQLite Task Queue、Outbox 和事件序号是控制链事实源。
3. Windows Desktop 只负责展示、通知、审批、用户控制和诊断入口。
4. Windows Worker 与 WPF UI 解耦；UI 关闭不得终止后台任务。
5. 普通低风险任务自动运行；Protected 写入、云端上传、发布、破坏性操作和显著费用必须人工批准。
6. 2.2.0 保留为稳定回滚基线，2.3.0 采用兼容扩展，不破坏现有配对凭据和基础 API。
7. 所有 Windows 交付来自原生 Windows CI 的预编译、可验证 Artifact。
8. 日常最终使用不得要求用户打开 Terminal、CMD 或 PowerShell。
9. Superpowers 作为开发治理、决策、证据和审批规则使用，不作为 WPF 或 Mac Core 的新增运行时依赖。

## 3. 当前仓库事实

### 3.1 Windows Desktop

当前仓库已具备：

- WPF 主程序与 Core 类库；
- MVVM 基础设施、异步命令和 UI Dispatcher；
- Mac Core REST 客户端；
- WebSocket 事件客户端、断线重连和 `after_sequence` 续传；
- Windows Credential Manager Token 存储；
- 任务列表虚拟化和增量归并；
- 安装、验证、诊断、回滚的预编译交付链；
- 原生 Windows CI 构建、打包、自检和哈希清单。

当前界面只有“总览”和“连接设置”两个标签。首页突出 REST/WS 延迟、任务数量和任务类型输入框，不能完成项目查看、任务全过程解释、结果消费、审批或故障处置。

### 3.2 Mac Core API

当前仓库已具备：

- `GET /api/v1/health`；
- 项目创建、列表和详情；
- 任务创建、列表、详情、取消和重试；
- 审批请求、批准和拒绝；
- 单个结果读取；
- WebSocket 事件与 Outbox 序号续传；
- Trace ID、统一错误和基础审计能力。

当前接口不足以完整支撑 2.3，包括：Dashboard 聚合、任务 DAG/节点详情、暂停/恢复、审批列表、结果列表、详细健康、脱敏日志查询和完整诊断信息。

## 4. 方案比较与决定

### 方案 A：先重做全部 UI，再补 API

优点是视觉变化快；缺点是大量页面只能依赖假数据或客户端拼装，容易形成不可验收的空壳。

### 方案 B：按“契约优先的纵向切片”并行扩展 API 与 UI

每个切片同时定义 DTO、服务状态、ViewModel、页面、错误语义和自动测试。先复用现有 2.2 API，再逐步增加兼容接口。

优点是每一步都有真实数据、可测试、可回滚；缺点是首个可见页面需要先完成少量契约工作。

### 方案 C：一次完成全部 2.3 API 与全部页面

优点是最终结构一次成形；缺点是变更面过大，测试定位困难，违背独立安装、验证和回滚原则。

### 决定

采用方案 B：契约优先的纵向切片。2.3 内部按应用壳与状态、Dashboard/Task、Approval/Result、Health/Diagnostics 四个切片推进。任何切片必须具备真实 API、自动测试、Windows CI、预编译包和回滚证据后，才进入下一切片。

## 5. 产品范围

### 5.1 2.3 必须交付

1. 完整左侧导航和全局连接状态。
2. Dashboard：运行中、等待审批、今日完成、异常、系统健康和最近结果摘要。
3. 收件箱/项目：项目列表、来源、状态、最近活动和原项目入口；在 Phase 3 未完成前必须使用明确空状态。
4. 任务中心：筛选、搜索、优先级、状态、真实进度、ETA、执行位置、重试和控制动作。
5. 任务详情：DAG、节点、事件时间线、输入、日志摘要、结果、错误、`trace_id`。
6. 结果与预览：文本、图片、视频、字幕和报告的安全预览模型；2.3 至少支持现有结果元数据与本地目录入口。
7. 审批中心：待审批列表、范围、风险、过期、批准、拒绝、原因和幂等防重放。
8. 自动化与计划：Connector、夜间窗口和 Morning Brief 在未实现时显示解释性空状态，不伪造运行状态。
9. 系统健康：Mac、Windows Desktop、版本、连接、存储、队列和依赖状态；未接入的 Worker、GPU、ComfyUI 明确标为“未接入”而不是“正常”。
10. 日志与诊断：按 `trace_id` 查询脱敏日志、错误码解释、诊断包预览和导出入口。
11. 设置与设备：配对、通知、主题、语言、更新渠道和权限说明。
12. 托盘、通知、窗口关闭最小化和无终端启动。
13. 更新失败自动回滚，保留 2.2.0 恢复入口。

### 5.2 明确不在 2.3 实现

- Generic Connector 文件生命周期和业务写回；
- Maotai 与视频助手实际接入；
- Windows Worker、GPU Scheduler、ComfyUI 任务领取与执行；
- BGE-M3、Qdrant、夜间批处理实际调度；
- 云端 Handoff 上传；
- 自动视频闭环。

这些功能可通过稳定契约和空状态预留展示位置，但不得用模拟数据冒充已实现能力。

## 6. 信息架构

左侧导航固定为：

1. 总览
2. 收件箱/项目
3. 任务中心
4. 结果与预览
5. 审批中心
6. 自动化与计划
7. 系统健康
8. 日志与诊断
9. 设置与设备

任务详情不是独立一级导航，而是从 Dashboard、项目或任务中心进入的详情路由。全局顶部区域仅保留产品名称、当前连接摘要、需要审批提示和自然语言目标入口。技术延迟指标下沉至系统健康。

## 7. Windows 应用架构

### 7.1 应用壳

`ShellWindow` 负责：

- 一级导航；
- 页面宿主；
- 全局连接和通知区域；
- 窗口、托盘和生命周期；
- 全局错误边界。

现有 `MainWindow` 不继续堆叠所有页面逻辑。迁移时保留现有启动和配对行为，通过兼容适配逐步替换。

### 7.2 页面 ViewModel

每个页面使用独立 ViewModel：

- `DashboardViewModel`
- `ProjectsViewModel`
- `TaskCenterViewModel`
- `TaskDetailViewModel`
- `ResultsViewModel`
- `ApprovalsViewModel`
- `AutomationViewModel`
- `HealthViewModel`
- `DiagnosticsViewModel`
- `SettingsViewModel`

ViewModel 只负责页面状态、命令和格式化，不直接持有 Token，不直接构造 HTTP 请求，不直接读写任意文件路径。

### 7.3 共享状态

拆分为可独立测试的状态仓库：

- `ConnectionStateStore`：连接、认证、重连和最后事件序号；
- `ProjectStateStore`：项目快照与增量事件；
- `TaskStateStore`：任务、节点、状态转换和本地筛选索引；
- `ApprovalStateStore`：审批状态、过期和本地防重复提交；
- `ResultStateStore`：结果清单、预览能力和来源；
- `HealthStateStore`：组件健康与更新时间；
- `NotificationStateStore`：信息、注意和审批三级通知。

状态仓库不得成为第二事实源。应用重启后应从 Mac Core 快照恢复，再按事件序号续传。

### 7.4 服务边界

- `IMacCoreClient`：REST 契约；
- `IEventStreamClient`：事件订阅与恢复；
- `ITokenStore`：Credential Manager；
- `ISettingsStore`：非敏感设置；
- `IFileOpenService`：只打开经过服务端或白名单验证的本地目录；
- `ITrayService`：托盘与窗口生命周期；
- `INotificationService`：Windows 通知；
- `IDiagnosticsExportService`：脱敏诊断包预览与导出；
- `IUpdateService`：版本清单、原子激活和回滚。

## 8. 任务状态与真实进度

UI 统一理解以下业务状态：

`discovered`、`queued`、`planning`、`waiting_input`、`waiting_approval`、`scheduled`、`running`、`quality_check`、`retrying`、`writing_back`、`completed`、`failed_retryable`、`failed_terminal`、`paused`、`canceled`。

Mac Core 在 2.3 初期未必产生全部状态。客户端必须容忍未知状态并显示原始值和“当前版本尚未识别”的解释，不把未知状态映射为完成或失败。

进度规则：

1. 只有执行器提供可信进度时显示百分比。
2. 无可信百分比时显示“第 N/M 步”和已耗时。
3. ETA 缺失时明确显示“暂无法估计”。
4. 任务详情必须展示当前执行位置、尝试次数、重试原因、错误码、可重试性和最后事件序号。
5. 不在 2.3 伪造 GPU、显存、Worker 或 ComfyUI 进度。

## 9. API 兼容扩展

现有 `/api/v1` 接口继续保留。2.3 增量采用兼容 DTO 和新端点，不进行破坏性替换。

### 9.1 必需新增接口

- `GET /api/v1/dashboard`
- `GET /api/v1/tasks/{id}/detail`
- `POST /api/v1/tasks/{id}/pause`
- `POST /api/v1/tasks/{id}/resume`
- `GET /api/v1/results`
- `GET /api/v1/approvals`
- `GET /api/v1/health/detailed`
- `GET /api/v1/logs?trace_id=`

现有取消、重试、项目列表、项目详情、单个结果、批准和拒绝接口继续复用。

### 9.2 Dashboard DTO

Dashboard 由服务端聚合，至少包含：

- 统计时间；
- 运行中任务数；
- 待审批数；
- 今日完成数；
- 异常数；
- 总体健康摘要；
- 最近任务；
- 最近结果；
- 需要用户操作的项目。

客户端不得为生成首页而发起大量并行列表请求后自行猜测统计口径。

### 9.3 Task Detail DTO

任务详情至少包含：

- Task 基础字段；
- `project_id`、`trace_id`、优先级和资源标签；
- 节点列表及依赖；
- 当前步骤和执行位置；
- 进度、ETA、尝试次数和重试原因；
- 事件时间线；
- 输入与输出引用；
- 结果引用；
- 错误码、影响、自动处理和可选动作；
- 最后事件序号。

在 TaskNode 持久化尚未实现时，接口可以返回空节点列表和明确能力标记，但不得构造虚假 DAG。

### 9.4 审批契约

审批列表返回：

- `approval_id`
- 动作和范围
- 风险等级
- 过期时间
- 状态
- `request_digest`
- 关联任务与项目
- 决策审计摘要

批准和拒绝请求必须携带 `request_digest`、原因和幂等键。输入、目标或文件清单变化后，旧批准自动失效。

### 9.5 结果契约

结果列表只返回安全元数据和经过许可的预览描述，不直接暴露任意绝对路径。打开目录动作必须通过白名单根目录和规范化路径验证。

### 9.6 详细健康契约

健康项统一返回：

- 组件 ID 和显示名称；
- 状态：`healthy`、`degraded`、`offline`、`not_configured`、`unknown`；
- 版本；
- 最近心跳；
- 用户影响；
- 自动处理；
- 建议动作；
- `trace_id` 或诊断引用。

## 10. 事件同步与断线恢复

1. Windows 保存最后已成功应用的 `sequence`。
2. 重连时使用 `after_sequence` 请求补发。
3. 每个事件按 `event_id` 和 `sequence` 幂等归并。
4. 发现序号跳跃时停止静默归并，触发有界快照重载并记录诊断事件。
5. 快照重载后继续从服务端确认的序号订阅。
6. 页面 ViewModel 不直接处理 WebSocket；事件先进入状态仓库，再由页面订阅变化。
7. 未知事件类型被记录并忽略，不导致整个事件流崩溃。

## 11. 审批、安全与治理

### 11.1 权限层级

- L0 只读：自动允许；
- L1 白名单派生写入：自动允许并审计；
- L2 业务写回：由 Connector 策略决定，必要时审批；
- L3 Protected/破坏性：默认拒绝，显式审批和备份；
- L4 云端/发布/显著费用：每次人工批准，带范围和过期时间。

2.3 的审批中心必须能准确展示这些级别，但不会提前实现尚不存在的 Connector 或云端执行。

### 11.2 Superpowers 治理映射

- 设计、计划、测试证据、安装证据和回滚证据作为独立文件提交；
- 文件状态遵循 Draft → Review → Approved → Released → Archived；
- 低风险项目内部 Draft 可自动创建和修改；
- 正式文件、Approved、Released 和 Protected 数据不得静默覆盖；
- 外部上传、发布、付费和破坏性操作仍由用户明确批准；
- 治理记录不包含 Token、密钥或 Protected 原文。

## 12. 错误处理与诊断

所有面向用户的错误至少包含：

- 发生阶段；
- 对当前任务或系统的影响；
- 系统已经执行的自动处理；
- 用户可选动作；
- 错误码；
- 可重试性；
- `trace_id`。

禁止只显示“连接失败”或直接展示原始异常堆栈。

诊断包默认脱敏，并在导出前显示文件清单。禁止包含 Credential、Token、Keychain 内容、Protected 原件、完整用户素材或未经许可的绝对路径。

## 13. 托盘、通知和生命周期

- 关闭主窗口默认最小化到托盘；
- 托盘菜单：打开控制中心、暂停自动化、Game Mode、查看待审批、退出 UI；
- 退出 UI 不代表停止 Mac Core 或未来 Worker；
- 通知分为信息、需要注意、需要审批；
- 不为每个后台节点弹出通知；
- 配对失效或认证失败必须明确提示，但不在通知中暴露地址以外的敏感信息。

Phase 2.3 中“暂停自动化”和“Game Mode”在后端能力尚未实现时显示不可用原因，不发送无效控制请求。

## 14. 更新与回滚

2.3 继续使用版本目录、哈希清单和原子激活：

1. 下载或安装前验证版本清单与 SHA-256；
2. 新版本安装到独立目录；
3. 启动自检成功后切换 `current`；
4. 自检失败自动恢复上一稳定版本；
5. 保留 2.2.0 恢复入口；
6. 用户设置和 Credential Manager 凭据不因回滚被删除；
7. 回滚不得覆盖或删除结果、证据和诊断记录。

## 15. 测试设计

### 15.1 Mac Core

- Dashboard 聚合口径测试；
- Task Detail 空 DAG 和真实节点两种响应测试；
- pause/resume 状态转换合法性测试；
- 审批列表、过期、`request_digest` 失效和重复点击测试；
- 结果列表路径脱敏测试；
- 详细健康状态测试；
- 按 `trace_id` 日志查询和秘密扫描测试；
- OpenAPI 向后兼容测试。

### 15.2 Windows Core 与 ViewModel

- 导航和页面生命周期；
- Dashboard 状态转换；
- 任务筛选、搜索、排序和未知状态；
- 真实百分比、步骤进度和“无法估计”显示；
- 断线、重连、重复事件和序号跳跃；
- 审批重复提交、本地忙碌状态和过期；
- 错误模型到用户文案映射；
- 日志与诊断脱敏；
- 更新失败回滚状态。

### 15.3 原生 Windows CI

CI 必须执行：

- 固定 .NET SDK；
- WarningsAsErrors；
- 单元测试、契约测试和 ViewModel 测试；
- WPF 编译；
- self-contained `win-x64` 发布；
- 主程序、诊断器和安装器 self-test；
- UI smoke：启动、导航、关闭到托盘、重开；
- PowerShell 5.1 脚本解析；
- ZIP 解压、清单和 SHA-256 复验；
- 秘密扫描和日志脱敏检查。

没有原生 Windows CI 输出时，不得标记 Windows 构建、启动或安装验收通过。

## 16. 2.3 内部交付切片

### Slice A：应用壳、导航、状态与契约骨架

- Shell、导航、全局状态和空页面；
- API DTO 与客户端接口；
- 现有配对和事件链兼容；
- 不改变 2.2 任务事实源。

验收：原生 Windows CI 可启动并切换页面；自动连接仍工作；无终端；2.2.0 可回滚。

### Slice B：Dashboard 与 Task Center

- Dashboard 聚合；
- 任务筛选、搜索和详情；
- 事件时间线、真实进度和错误语义；
- 取消、重试及后端支持时的暂停/恢复。

验收：现有真实任务可完整展示；断线续传不重复；用户 10 秒内判断系统状态和待办。

### Slice C：Approval Center 与 Result Center

- 审批列表、批准、拒绝、过期和防重复；
- 结果列表、来源和安全打开目录；
- 明确空状态。

验收：重复点击不产生重复副作用；结果来源可追踪；禁止任意路径打开。

### Slice D：Health、Diagnostics、Tray 与 Update

- 详细健康；
- 脱敏日志和诊断包；
- 托盘、通知和窗口生命周期；
- 更新失败回滚。

验收：故障不要求用户运行脚本；诊断不含秘密；更新失败自动恢复上一稳定版本。

## 17. 可用性验收映射

2.3 Release Candidate 必须满足：

1. 双击桌面图标启动，不出现终端窗口。
2. 首页 10 秒内回答：系统是否正常、正在做什么、是否需要批准、结果在哪里。
3. 任务详情显示真实阶段、DAG 或明确无 DAG、进度/步骤、执行位置和 ETA 或无法估计说明。
4. 断网、Mac 重启和 Windows UI 重开后自动恢复，并按序号续传。
5. 错误包含错误码、阶段、影响、自动处置、可重试性和 `trace_id`。
6. 审批重复点击无重复副作用；范围变化后旧批准失效。
7. 结果可预览或明确说明当前预览能力，并可追踪来源和安全打开目录。
8. 技术延迟位于系统健康，不占据普通用户首页。
9. 日志和诊断默认脱敏。
10. 更新失败可回滚到 2.2.0，只有绿色原生 Windows CI Artifact 可交付。

## 18. 风险与控制

### 风险 1：现有 API 数据不足

控制：空字段和能力标记必须显式；按纵向切片增加契约；禁止 UI 伪造。

### 风险 2：单个主 ViewModel 继续膨胀

控制：按页面和状态仓库拆分；共享服务通过接口注入；禁止页面直接调用网络和凭据。

### 风险 3：审批安全语义不完整

控制：引入 `request_digest`、幂等键、过期和审计；服务端是最终判定者，客户端防重只是辅助。

### 风险 4：更新覆盖稳定版本

控制：版本目录、原子激活、健康探针和保留上一版；不原地覆盖。

### 风险 5：文档范围扩张到 Phase 3–11

控制：2.3 仅预留契约和空状态；实际 Connector、Worker 和闭环按后续独立规格实施。

## 19. 未知项及处理

以下内容当前仓库证据不足，不能写成已完成：

- TaskNode 的正式持久化结构；
- pause/resume 的服务端状态转换规则；
- Dashboard 的最终统计时间边界；
- 本地结果目录的白名单根集合；
- Windows 通知和托盘所采用的具体封装库；
- 更新签名机制的最终证书和分发渠道。

这些未知项在实施计划中通过仓库盘点、契约测试和最小技术验证解决，不重新选择冻结技术栈，也不在用户电脑上试错。
