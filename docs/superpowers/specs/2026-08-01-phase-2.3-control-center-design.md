# Picotoo Pet V2.3 Windows Control Center 冻结设计规格

- 文档状态：**Approved / Frozen**
- 冻结日期：2026-08-01
- 基线分支：`main`
- 基线提交：`4ef2634ec24666d8995874d44bbf5b0e238d450a`
- 目标版本：`2.3.0`
- 设计依据：`Picotoo Pet V2.2–V3 Complete Handoff v2.0`
- 配套合同：`Connector Contract v1`、`Handoff / Return Contract v1`
- 实施原则：契约优先、纵向切片、TDD、原生 Windows CI、预编译交付、可回滚

## 1. 冻结结论

Phase 2.3 将现有 Windows Desktop 从“连接与任务链路工程切片”升级为 Picotoo Pet 的唯一日常 Control Center。它负责项目、任务、结果、审批、健康、自动化、诊断和用户控制，但不成为任务事实源，不直接执行 ComfyUI、媒体流水线或外部开发 Provider。

本规格已经吸收新的完整交接基线与 Superpowers 治理原则。除非后续出现可复现的不可行硬证据，否则实施阶段不得重新选择总体架构、重新修补 V1、把开发试错转移到用户电脑，或用模拟数据冒充未完成能力。

## 2. 证据与决策优先级

出现冲突时按以下顺序处理：

1. 用户在当前对话中的明确决定；
2. Complete Handoff v2.0 中标记为“实机确认、冻结决策、用户免验”的内容；
3. 当前 GitHub `main` 的可读取代码、测试、CI 与发布证据；
4. 已批准的 Superpowers 治理规则；
5. 本规格的兼容性推导；
6. 外部 Provider 官方能力，仅在对应阶段实施当天重新核对。

所有判断必须区分：

- **FACT**：仓库、CI、实机报告或哈希已经证明；
- **DECISION**：用户或冻结基线已经确认；
- **INFERENCE**：从事实推导，但尚未实机证明；
- **UNKNOWN**：当前证据不足；
- **NOT_RUN**：缺少原生环境，不能宣称通过；
- **USER_WAIVED**：用户免验，不等于性能通过。

## 3. 自主执行边界

### 3.1 可自主推进

以下操作低风险、可逆且位于项目内部，可在隔离分支直接推进：

- 读取仓库、文档、测试和 CI；
- 创建或修改 Draft/Review 设计、计划和测试证据；
- 创建隔离分支、worktree、测试 fixture 和兼容 DTO；
- 运行本地或 CI 自动测试；
- 修改尚未发布的实现并提交小步 commit；
- 根据失败证据修正设计细节，但不得改变冻结总体边界。

### 3.2 必须人工批准

以下操作不得自行执行：

- 修改 `main`、合并 PR、正式发布或部署；
- 安装/卸载软件，修改服务、注册表、防火墙、PATH、端口或系统策略；
- 删除、覆盖 Approved/Released、Protected 或正式业务数据；
- 上传文件到外部 Provider、启用付费服务或产生费用；
- 代码合并、公开发布、云端 Handoff、Provider 切换；
- 任何不可逆或影响用户稳定基线的操作。

文件生命周期遵循：`Draft → Review → Approved → Released → Archived`。Draft 可自动修改；Approved/Released 不得静默覆盖。

## 4. 已验证仓库基线

### 4.1 Windows Desktop 已有能力

- .NET WPF、MVVM 基础、异步命令和 UI Dispatcher；
- 长生命周期 REST 客户端；
- WebSocket 事件流、指数退避、序号续传和幂等归并；
- Windows Credential Manager Token 存储；
- 虚拟化任务列表与增量更新；
- 诊断器、安装器、验证器、版本目录、哈希清单和回滚入口；
- 原生 Windows CI 的 build、publish、self-test 和预编译 Artifact。

当前 UI 仅有“总览”和“连接设置”，突出 REST/WS 延迟、任务数量和技术任务类型输入，不能完成项目理解、任务全过程解释、结果消费、审批或故障恢复。

### 4.2 Mac Core 已有能力

- `GET /api/v1/health` 与能力接口；
- Project 创建、列表、详情；
- Task 创建、列表、详情、取消、重试；
- Approval 请求、批准、拒绝；
- 单个 Result 元数据读取；
- SQLite Task Queue + Outbox；
- WebSocket 事件序号、断线补发；
- Trace ID、统一错误、基础审计和 Result Store。

### 4.3 尚未具备

- Dashboard 服务端聚合；
- TaskNode/DAG 的完整持久化和详情接口；
- pause/resume 完整状态语义；
- Approval 列表与 `request_digest` 防重放；
- Result 列表、预览能力与安全目录入口；
- 详细健康与脱敏日志查询；
- Generic Connector、Windows Media Worker、夜间调度、Handoff Manager 和 Dev Broker 的运行实现。

## 5. 产品定位与职责边界

| 组件 | 必须负责 | 明确不负责 |
|---|---|---|
| Mac Core | 事实源、任务编排、权限、审计、结果索引、事件服务 | 重型 GPU 推理、Windows UI |
| Windows Control Center | 展示、通知、审批、用户控制、诊断入口、结果消费 | 任务事实源、直接执行 ComfyUI、绕过权限写回 |
| Windows Worker | 后续领取任务、执行、进度、取消、恢复、结果校验 | 自主决定业务目标、绕过审批 |
| Connector | 后续发现、解析、Schema 映射、去重、受控写回 | 修改 Protected 原件、嵌入业务 AI 逻辑 |
| External Provider | 后续在批准沙盒中执行专业工程任务 | 事实源、主 UI、直接 main/发布/Protected 访问 |

Control Center 关闭后后台核心服务不得停止；2.3 只保持已有连接订阅，不提前实现 Worker。

## 6. 信息架构

一级导航冻结为：

1. 总览
2. 收件箱 / 项目
3. 任务中心
4. 结果与预览
5. 审批中心
6. 云端开发
7. 自动化与计划
8. 系统健康
9. 日志与诊断
10. 设置与设备

任务详情是二级详情路由，不占一级导航。

“云端开发”在 2.3 只交付合同就绪的解释性空状态、Handoff 历史模型占位和权限说明；不得安装、调用或模拟 Grok Build、Codex、Claude Code。真实 Handoff Manager 属于 Phase 10A，Dev Broker/Provider Adapter 属于 Phase 10B。

## 7. 首页十秒判定标准

总览必须在十秒内回答：

1. 系统是否正常；
2. 正在处理哪个项目和任务；
3. 当前阶段、步骤、已用时与 ETA 是否可信；
4. 是否需要用户操作或审批；
5. 最近结果在哪里、是否已写回。

首页不得展示 REST/WS p95 等工程指标；这些数据下沉到系统健康。所有空状态必须解释“为什么为空、系统接下来会做什么、用户是否需要操作”。

## 8. 应用架构

### 8.1 Shell

`ShellWindow` 负责：

- 一级导航和页面宿主；
- 全局连接摘要、审批提示和通知；
- 深色/浅色主题、Windows 缩放和键盘导航；
- 托盘与窗口生命周期；
- 全局错误边界；
- 无终端启动。

现有 `MainWindow` 作为迁移入口逐步收缩，不继续承载网络、任务、设置和所有页面状态。

### 8.2 页面 ViewModel

- `DashboardViewModel`
- `ProjectsViewModel`
- `TaskCenterViewModel`
- `TaskDetailViewModel`
- `ResultsViewModel`
- `ApprovalsViewModel`
- `CloudDevelopmentViewModel`
- `AutomationViewModel`
- `HealthViewModel`
- `DiagnosticsViewModel`
- `SettingsViewModel`

ViewModel 只负责页面状态、命令和展示格式，不持有明文 Token，不拼接任意文件路径，不直接构造 HTTP 请求。

### 8.3 共享状态

- `ConnectionStateStore`
- `CapabilityStateStore`
- `ProjectStateStore`
- `TaskStateStore`
- `ApprovalStateStore`
- `ResultStateStore`
- `HealthStateStore`
- `NotificationStateStore`

状态仓库是 UI 缓存，不是第二事实源。启动后先读取 Mac Core 快照，再按服务端确认的 `sequence` 续传。

### 8.4 协调器与服务

- `IControlCenterBootstrapper`：启动、配对、初始快照和页面就绪；
- `IStateSyncCoordinator`：REST 快照与 WebSocket 增量同步；
- `IMacCoreClient`：兼容 REST 契约；
- `IEventStreamClient`：事件订阅、补发、断线恢复；
- `ICapabilityService`：依据服务端能力控制页面和命令；
- `ITokenStore`：Credential Manager；
- `ISettingsStore`：非敏感设置；
- `IFileOpenService`：仅打开服务端批准且通过根目录验证的路径；
- `ITrayService`：托盘与窗口生命周期；
- `INotificationService`：信息、注意、审批三级通知；
- `IDiagnosticsExportService`：脱敏诊断清单和导出；
- `IUpdateService`：版本清单、原子激活和回滚。

## 9. 能力协商与 2.2 兼容

2.3 必须兼容 2.2 Mac Core。客户端不得仅凭版本号猜能力，而应读取 `GET /api/v1/capabilities`。

能力键至少包括：

- `dashboard`
- `task_detail`
- `task_pause_resume`
- `approval_list`
- `approval_digest`
- `result_list`
- `result_preview`
- `health_detailed`
- `logs_query`
- `manual_goal`
- `connector_contract_v1`
- `handoff_contract_v1`

缺少能力时：

- 页面显示解释性空状态；
- 不发送无效命令；
- 不伪造数据；
- 现有健康、任务列表、取消、重试和事件链继续工作。

## 10. 任务状态、DAG 与真实进度

统一理解以下状态：

`discovered`、`queued`、`planning`、`waiting_input`、`waiting_approval`、`scheduled`、`running`、`quality_check`、`retrying`、`writing_back`、`completed`、`failed_retryable`、`failed_terminal`、`paused`、`canceled`。

未知状态必须显示原始值与“当前客户端尚未识别”，不得映射成成功或失败。

进度规则：

1. 只有执行器或可计数节点提供真实数据时显示百分比；
2. 不可量化时显示“阶段 N/M + 已用时”；
3. ETA 必须包含置信度；样本不足显示“暂不可估计”；
4. DAG 不存在时显示“当前任务没有节点数据”，不得生成虚假节点；
5. 详情显示执行位置、attempt、重试原因、降级参数、剩余上限、heartbeat、`last_sequence`；
6. 2.3 不伪造 GPU、显存、ComfyUI 或 Worker 进度。

## 11. Control Center API 兼容扩展

现有 `/api/v1` 保留。新增接口：

- `GET /api/v1/dashboard`
- `GET /api/v1/tasks/{task_id}/detail`
- `POST /api/v1/tasks/{task_id}/pause`
- `POST /api/v1/tasks/{task_id}/resume`
- `GET /api/v1/results`
- `GET /api/v1/approvals`
- `GET /api/v1/health/detailed`
- `GET /api/v1/logs?trace_id=`

现有项目、任务、取消、重试、结果详情、审批决策和 WebSocket 接口继续复用。

### 11.1 Dashboard

服务端统一统计口径，返回：

- `generated_at`
- `running_count`
- `waiting_approval_count`
- `completed_today_count`
- `attention_count`
- `health_summary`
- `recent_tasks`
- `recent_results`
- `action_items`
- `capabilities`

客户端不得通过大量并行请求自行猜测统计口径。

### 11.2 Task Detail

返回：

- Task 基础字段；
- 业务标题、`project_id`、`trace_id`、优先级、资源标签；
- 节点和依赖；
- 当前阶段、步骤、执行位置；
- 进度来源、百分比、已用时、ETA 和置信度；
- attempt、重试原因、降级和剩余上限；
- 事件时间线；
- 输入、Artifact 和 Result 引用；
- 错误码、阶段、影响、自动处置、可重试性、用户动作；
- 最后事件序号；
- 能力标记。

### 11.3 Approval

审批列表与决策必须支持：

- `approval_id`
- action、scope、risk、expires_at、state
- `request_digest`
- task/project 关联
- 文件/目标/预算摘要
- 决策原因和审计摘要
- `Idempotency-Key`

输入、目标、Provider、预算或文件清单变化后，旧 `request_digest` 失效。客户端防重复点击只是辅助，服务端必须保证幂等。

### 11.4 Result

结果列表返回安全元数据、来源、哈希、质量摘要、写回状态和预览能力，不直接暴露任意可执行路径。打开目录必须通过白名单根、路径规范化和链接逃逸检查。

### 11.5 Detailed Health

健康项统一返回：

- component_id、display_name
- status：`healthy | degraded | offline | not_configured | unknown`
- version、last_heartbeat
- resource_summary
- user_impact、automatic_action、recommended_action
- trace_id 或 diagnostics_ref

未实现 Worker/Connector/Provider 时必须显示 `not_configured`，不能显示 healthy。

## 12. 事件一致性与恢复

1. 每个事件包含 `event_id`、`sequence`、`occurred_at`、`task_id`、`project_id`、`trace_id`、`type`、`payload_version`；
2. 客户端按 `event_id + sequence` 幂等归并；
3. 重连携带 `after_sequence`；
4. 发现序号跳跃时记录诊断，暂停静默归并，执行有界快照重载；
5. 快照完成后从服务端确认序号继续；
6. 未知事件记录后忽略，不崩溃；
7. 不允许用“刷新全表”掩盖事件丢失；
8. 外部副作用节点必须使用 `idempotency_key`。

## 13. 错误、通知与诊断

用户错误模型至少包含：

- `code`
- `stage`
- `summary`
- `impact`
- `automatic_action`
- `retryable`
- `suggested_actions`
- `trace_id`

禁止只显示“连接失败”或原始异常堆栈。

通知分三级：

- 信息：完成、恢复、普通状态变化；
- 需要注意：可重试失败、磁盘水位、连接降级；
- 需要审批：Protected、云端、发布、费用、合并。

诊断包导出前必须展示文件清单，默认脱敏，禁止 Token、Keychain/Credential 明文、Protected 原件、未批准媒体和任意用户目录内容。

## 14. 托盘、生命周期与可访问性

- 关闭窗口默认最小化到托盘；
- 托盘菜单包含：打开控制中心、暂停自动化、Game Mode、查看待审批、退出 UI；
- 未实现的后端能力必须禁用并解释原因；
- 退出 UI 不停止 Mac Core 或未来 Worker；
- 支持深色/浅色、Windows 缩放、键盘操作和中文优先；
- 不依赖终端作为日常入口。

## 15. 更新与回滚

1. 安装包验证 manifest 和 SHA-256；
2. 新版本进入独立版本目录；
3. 启动 self-test 成功后原子切换 `current`；
4. 失败自动恢复上一稳定版本；
5. 2.2.0 保留为恢复基线；
6. 回滚不删除设置、Credential、结果、证据或审计；
7. 只有原生 Windows CI 绿色 Artifact 可供用户安装；
8. 用户电脑不编译源码、不安装开发 SDK 进行试错。

## 19. 代码质量约束

- 所有新增代码带清晰、对齐的中文注释；
- 一个文件只承担一个主要职责；
- 不新增无必要第三方依赖；
- 不在 ViewModel 中直接访问网络、Token 或任意文件；
- 不吞异常，不使用静默 fallback；
- 不使用假进度、假健康或假业务数据；
- 所有外部副作用都有幂等键、审计和明确失败状态；
- 复杂状态转换必须有失败测试先行；
- 每个完成声明附新鲜验证输出。

## 20. 2.3 Release Candidate 验收

1. 双击桌面图标启动，全程无终端；
2. 首页十秒内回答系统、任务、进度、审批和结果五个问题；
3. 任务详情显示真实阶段、DAG 或明确无 DAG、步骤、ETA/不可估计、执行位置；
4. 断网、Mac 重启和 UI 重开后按序恢复；
5. 错误包含 code、stage、impact、automatic_action、retryable、trace_id；
6. 审批重复点击无重复副作用，范围变化旧批准失效；
7. 结果可追踪来源并安全打开目录；
8. 技术延迟位于健康页；
9. 日志和诊断默认脱敏；
10. 更新失败可回滚到 2.2.0；
11. 只有绿色原生 Windows CI Artifact 可交付；
12. 高负载性能仍标记 USER_WAIVED，直到 3.x/6.x 实机重新量化。
