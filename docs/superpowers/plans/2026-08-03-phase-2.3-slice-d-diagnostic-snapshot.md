# Phase 2.3 Slice D Diagnostic Snapshot Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver one stable end-to-end `system.diagnostic_snapshot` task from Windows creation through Mac Core queueing, Mac Worker execution, atomic result persistence, bounded observation, cancellation, retry, and result viewing.

**Architecture:** Extend the existing SQLite queue and content-addressed ResultStore rather than introducing a second data plane. The Worker remains single-task and explicitly registered; diagnostic collection runs in a killable macOS process group, while the parent owns leases, cancellation and the atomic task/result commit. Windows consumes fixed API contracts and renders a fixed result view with bounded asynchronous recovery.

**Tech Stack:** Python 3.12, FastAPI, Pydantic v2, SQLite, macOS launchd/arm64 packaging, .NET 10 WPF, System.Text.Json, GitHub Actions native macOS/Windows CI.

## Global Constraints

- Fixed task type: `system.diagnostic_snapshot`.
- Worker supported types remain exactly `system.noop` and `system.diagnostic_snapshot`.
- Historical `analysis` tasks must remain untouched and unsupported.
- Diagnostic payload schema version is `1.0`; allowed sections are `core`, `worker`, and `queue`.
- Diagnostic result maximum is 64 KiB UTF-8 JSON.
- Task timeout is 30 seconds; child-process termination grace is at most 5 seconds.
- Worker remains single-task and serial.
- No Provider, model, internet, cloud upload, project scan, log-body capture, file enumeration, Token, credential, IP, MAC address, or user path collection.
- Windows fallback polling is bounded: 1 second initial, exponential backoff to 10 seconds, 2-minute observation window.
- User machines consume precompiled packages only; no source build or SDK installation.
- PR remains Draft and must not merge to `main`.
